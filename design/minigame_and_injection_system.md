# 小游戏与玩家产出注入系统设计

## 1. 设计理念

### 核心定位

玩家与女主林夏共同参加帧语·新星叙事大赛，制作一款**线性 Gal Game**（异世界魔法学院题材）。

- **故事骨架**（章节结构、情节走向）由开发者预制，固定不变
- **创意填充**（主角人设、配角性格、关键台词、世界观小设定）由玩家在游戏过程中决定
- **LLM 实时生成**完整的 AVG 内容——不是预制文本的变量替换，而是基于固定骨架 + 玩家创意输入的现场创作
- **林夏是大方向确认者**，玩家决定角色"活法"的细节
- **最终产品**是一款可玩的 Gal Game，每个玩家的产出因创意填充不同而独一无二

### 生产模型

```
开发者预制（固定）:
├── 章节结构（5 章）
├── 情节走向（起承转合）
└── 触发节点（哪些位置需要玩家输入）

玩家填充（个人化）:
├── 主角人设（名字、出身、性格）
├── 配角性格（从预设标签中选）
├── 关键台词（小游戏产出）
└── 世界观小设定（魔法属性、社团等）

LLM 实时生成:
└── 按骨架 + 玩家设定 → 生成完整 AVG DSL
	（不是润色，是在约束框架内现场写）
```

### 三层分工

| 层级 | 角色 | 控制内容 |
|------|------|---------|
| 宏观 | 开发者预制 | 故事结构、主线走向、叙事节奏（固定） |
| 中观 | 林夏确认 + 玩家创意填充 | 角色设定、性格标签、世界观细节 |
| 微观 | 玩家小游戏 | 关键台词、分支逻辑、Bug 修复 |

### 关键原则

1. **玩家不是甲方**：不会被问"你想做什么 AVG"——林夏已经决定了方向
2. **玩家是创意填充者**：在固定走向中定义角色是什么样的人
3. **两个玩家的作品不同**：不是因为剧情走向不同，而是因为角色"活法"不同
4. **LLM 是执行编剧**：有明确的骨架约束，根据玩家设定现场写台词，不是万能编剧
5. **5% 的个人印记 > 100% 的 AI 生成**：玩家补的那句台词比整篇 AI 剧本更有记忆点

## 2. 创意填充流程

### 2.1 时间轴总览

```
Day 1-3: 概念期 ─── 确定"做什么"+"角色是谁"
  ├─ Day 1 晚: 林夏提议方向（魔法学院异世界）→ 玩家确认
  ├─ Day 2 上午: 主角设计 → 玩家填人设（名字/出身/性格）
  ├─ Day 2 下午: 林夏展示大纲 + 配角提案 → 玩家选配角性格
  └─ Day 3: 正式开工，第一个工单出现

Day 3-15: 前期开发 ─── 第一章~第二章
  ├─ 工单: 实现开场场景 → 对话补全小游戏
  ├─ 工单: 实现角色相遇 → 对话补全/伪代码拼图
  └─ ★ 里程碑 25%: 第一次 Demo → 看到主角/配角按自己设定说话

Day 15-30: 中期开发 ─── 第三章~第四章
  ├─ 工单: 写关键剧情场景 → 对话补全
  ├─ 工单: 实现分支逻辑 → 伪代码拼图
  ├─ 工单: 调试演出 → Bug 修复找茬
  └─ ★ 里程碑 50%: 第二次 Demo → 看到前半段完整故事

Day 30-45: 后期打磨 ─── 第五章 + 收尾
  ├─ 工单: 高潮/结局 → 对话补全
  ├─ 工单: 全局测试 → Bug 修复
  └─ ★ 里程碑 75%/最终: 完整 Demo
```

### 2.2 概念期详细设计（Day 1-3）

#### 总原则

- 故事大方向（魔法学院异世界 Gal Game）是**林夏提出、开发者预设的**
- 玩家决定的是"这个固定框架里的角色是什么样的人"
- 概念期的交互是**林夏主导对话 → 系统弹出设计面板 → 玩家填选 → 林夏回应**

#### Day 1 晚 — 方向确认

沿用已有的 `day1_night_plan` topic，不改大结构。

```
林夏主导对话:
  "异世界这个主题... 我有一个想法"
  "你知道魔法学院那种设定吗？"
  "我觉得可以做一个主角进入异世界魔法学院的故事"
  "素材包里有那么多角色立绘可以用"

玩家: 自由回应（同意/聊两句）

林夏:
  "好！那大方向就这个！明天我先把故事大纲理一理"
  "你先想想... 主角应该是什么样的人？"
  [TOPIC_COMPLETE]
```

**数据捕获**：无（方向是固定的，这段对话只是叙事铺垫和关系营造）

#### Day 2 上午 — 主角设计（核心创意入口）

**触发方式**：新的 chapter step，林夏 LinkChat 发消息引导玩家打开 DevTool。

```
林夏: "昨晚说的，你想好主角的人设了吗？"
林夏: "我整理了一个角色设计表，在开发工具里"
林夏: "你来填主角的，配角我有想法等会跟你说"
→ 系统解锁 DevTool APP（或游戏编辑器界面）
→ 玩家打开后弹出「角色设计面板」
```

**角色设计面板（交互式选择界面，非表单）**：

```
┌─ 主角设计 ──────────────────────────────────┐
│                                              │
│  ✏️ 名字: [____________]                     │
│                                              │
│  🏠 出身:                                    │
│    ○ 王国贵族之女（名门出身，有包袱）          │
│    ○ 边境村庄少女（朴素天然，什么都新鲜）       │
│    ○ 流浪孤儿（不知道自己的过去）              │
│                                              │
│  💫 性格:                                    │
│    ○ 元气开朗（说干就干型）                    │
│    ○ 安静内敛（默默观察型）                    │
│    ○ 傲气倔强（不服输型）                      │
│                                              │
│  林夏💬: "边境村庄挺好的，                    │
│   那样进入学院的反差感会更强～"                 │
│                                              │
│                              [确认设计 ✓]    │
└──────────────────────────────────────────────┘
```

**关键设计要点**：

- **只有 3 个字段**（名字 + 出身 + 性格），轻量
- **每个选项旁有林夏的倾向提示**（她更喜欢某个选项，但不强迫）
- **选项由开发者预设**——确保每个选项都能被后续 LLM 生成支持
- 玩家选了和林夏偏好不同的 → 她尊重但微微失落（关系微调）

**数据捕获**：

```json
{
  "protagonist_name": "艾拉",
  "protagonist_origin": "border_village",
  "protagonist_personality": "energetic"
}
```

**完成后**：林夏通过 LinkChat 回应玩家的选择

```
林夏: "边境少女啊！那开场可以是她第一次进城的情景"
林夏: "性格元气的话，和学院里那些贵族小姐的反差一定很有趣"
林夏: "好，我记下了，继续弄大纲去～"
```

### 2.3 创意决策触发方式总结

| 触发方式 | 内容 | 时间点 |
|---------|------|--------|
| **林夏 LinkChat 话题** | 大方向确认 | Day 1 晚 |

### 2.4 创意数据的后续用途

概念期捕获的数据（主角人设、配角性格标签）注入 LLM 的生成 context：

```
protagonist:
  name: "艾拉"
  origin: "border_village"    → 影响主角的说话方式、世界认知
  personality: "energetic"    → 影响主角的反应模式

supporting_characters:
  prince:
	personality: "kuudere"    → 影响王子的台词风格和互动方式
  villainess:
	personality: "tsundere"   → 影响恶役小姐的行为模式
```

这些数据在整个开发期持续影响 LLM 生成的每一段对话。

## 3. 小游戏清单

### 3.1 对话补全（核心小游戏）

**体验定位**：给 AVG 角色写台词 — "这句话是我写的！"

**核心 Mechanic：三选项 + 自由输入**

#### 界面布局

```
┌─ 场景展示区 ─────────────────────────────────┐
│  [bg: 雨中的公交站]                           │
│                                              │
│  女主: "你真的要走吗？"                        │
│  主角: "________________"   ← 待补全          │
│  女主: "...我知道了。"                         │
│                                              │
│  当前情绪: [犹豫] [不舍]                       │
└──────────────────────────────────────────────┘

┌─ 选项区 ─────────────────────────────────────┐
│                                              │
│  A. "对不起，我必须去"                         │
│  B. "不是想走，是不得不走"                      │
│  C. "......"                                 │
│                                              │
│  ┌──────────────────────────┐               │
│  │ 自由输入 (≤20字)          │    [提交PR]   │
│  └──────────────────────────┘               │
└──────────────────────────────────────────────┘
```

#### 玩法

1. 系统展示 AVG 场景的上下文（前后台词 + 背景 + 角色情绪）
2. 提供 **3 个由 LLM 预生成的候选台词**（覆盖不同风格/语气）
3. 额外提供一个 **LineEdit 自由输入框**（≤20字）
4. 玩家选择一个选项或自行输入
5. 提交后进入 **林夏 Code Review 流程**（见第 4 节）

#### 审查规则

- **选择预设选项** → 自动 APPROVE（选项由 LLM 预生成，已保证质量）
- **自由输入** → 走完整 Code Review（林夏通过 LinkChat 审查）

#### 候选选项生成 Prompt

```
你是一个 AVG 台词设计师。根据以下场景信息，为空缺台词生成 3 个候选选项。

场景情绪: {{scene_mood}}
前文: {{previous_dialogue}}
后文: {{following_dialogue}}
说话角色: {{character_name}}
角色性格: {{character_profile}}

要求:
- 3 个选项覆盖不同风格: 一个直接、一个含蓄、一个沉默/极简
- 每个选项 ≤20 字
- 符合角色性格和场景基调
- 与前后文自然衔接

输出 JSON:
[
  {"text": "对不起，我必须去", "style": "direct"},
  {"text": "不是想走，是不得不走", "style": "subtle"},
  {"text": "......", "style": "minimal"}
]
```

#### 触发时机

- DevWork 工作时段中随机触发
- Story Director 在关键剧情节点主动触发

#### 产出类型

- `dialogue_fill`：一句具体的角色台词
- 直接嵌入最终 AVG 的对应位置

### 3.2 伪代码拼图 — 可视化流程图组装

**体验定位**：拖拽连线"编程" — "我在写代码！"

**核心 Mechanic：简化版连线流程图（类似 Unreal Blueprint 但极度简化）**

#### 界面布局

```
┌─ 任务面板 ──────────────────────────────────┐
│ 林夏: "如果主角选择坦白就切到告白场景，      │
│       选择隐瞒就回教室继续上课"               │
└──────────────────────────────────────────────┘

┌─ 流程图工作区 ───────────────────────────────┐
│                                              │
│  ┌──────────┐                                │
│  │ 🔀 选择   │                               │
│  │ ┌──────┐ │    ┌──────────┐                │
│  │ │ 坦白 ├─┼───▶│ 🎨 效果   │──▶ [📍 告白]  │
│  │ └──────┘ │    │ 背景=夕阳 │               │
│  │ ┌──────┐ │    │ 音乐=温柔 │               │
│  │ │ 隐瞒 ├─┼──▶ └──────────┘               │
│  │ └──────┘ │              [📍 教室]          │
│  └──────────┘                                │
│                                              │
├─ 积木库 ────────────────────────────────────┤
│ [🔀 选择] [❓ 条件] [🎨 效果] [📍 跳转]      │
│ [🔊 音效] [⏸ 等待] [💬 台词]                │
└──────────────────────────────────────────────┘
```

#### 积木类型

| 积木 | 功能 | 交互方式 |
|------|------|---------|
| 🔀 选择块 | 包含 2-3 个选项槽，每个选项引出一条连线 | 从工作区拖出 |
| 🎨 效果块 | 下拉选择背景/音乐（从素材包的有限列表中选） | 点击下拉菜单 |
| 📍 跳转块 | 下拉选择目标场景 | 点击下拉菜单 |
| 💬 台词块 | 显示一句预设台词（不可编辑） | 只读展示 |
| ❓ 条件块 | 如果 XX 则... 否则... | 选择条件变量 |

#### 操作流程

1. 从积木库**拖出积木**到工作区
2. 点击积木上的**连接点**，**拖拽连线**到下一个积木
3. 点击积木**打开参数面板**（下拉选择，不需要打字）
4. 点击 `[▶ 编译]`：
   - ✅ 全部分支连通 → "编译通过！" 动画 + 林夏: "逻辑没问题！"
   - ❌ 有悬空分支 → 高亮提示 "这个分支没有连到终点" → 玩家修复

#### 难度曲线

| 游戏阶段 | 积木数量 | 复杂度 |
|---------|---------|--------|
| 早期（Day 3-10） | 3 个 | 1 个选择 + 2 个跳转 |
| 中期（Day 11-25） | 5-6 个 | 选择 + 效果 + 跳转 |
| 后期（Day 26-40） | 7-8 个 | 嵌套条件 + 多效果 |
| **永远不超过 10 个积木** | — | 保持轻度 |

#### 乐趣来源

- **连线的满足感**（像 Flow Free / 连连看的变种）
- **"编译通过"的成就感**（程序员的经典快乐）
- **参数选择有审美空间**（选夕阳还是星空？选钢琴还是吉他？）
- **林夏的"代码审查"反馈**（"写得不错嘛！"）

#### 触发时机

- DevWork 工作时段，出现分支逻辑任务时

#### 产出类型

- `code_logic`：条件分支结构
- 映射为 AVG DSL 的选择/跳转逻辑

### 3.3 Bug 修复 — 场景找茬

**体验定位**：轻松的找茬 — "我找到了 Bug！"

**核心 Mechanic：AVG 场景回放 + 错误点击**

#### 界面布局

```
┌─ 场景回放区 ─────────────────────────────────┐
│                                              │
│  [AVG 场景自动播放中...]                      │
│                                              │
│  角色: "我很开心能见到你！" 😢 ← 表情bug!      │
│                                              │
│  玩家点击 → 场景暂停                          │
│                                              │
├──────────────────────────────────────────────┤
│  ❌ 这里有什么问题？                          │
│  A. 表情和台词不匹配                          │
│  B. 背景音乐不对                              │
│  C. 转场效果有误                              │
│  D. 没有问题                                  │
├──────────────────────────────────────────────┤
│  已发现: 🐛 1/3     场景进度: ▓▓▓▓░░░░       │
└──────────────────────────────────────────────┘
```

#### 玩法细节

1. 一段 **10-15 句的场景**自动播放，内含 **3 个预设 bug**
2. 玩家在播放过程中**点击暂停**并指出问题
3. 选择正确的问题类型 → "Bug 修复！" 动画 + 反馈文字
4. 全部找到 → "QA 满分！"
5. 找不全 → "还有些小问题，不过不影响发布"

#### Bug 类型

| Bug 类型 | 示例 |
|---------|------|
| 表情错误 | 台词说"我很开心"但表情是 😢 |
| BGM 错误 | 白天阳光场景配了深夜氛围 BGM |
| 角色位置跳变 | 上一句还在左边，突然跳到右边 |
| 名字错误 | 角色称呼用错了名字 |

#### 重要说明

- **Bug 是预设的伪 bug，修不修复对最终 AVG 项目无实际影响**
- 目的纯粹是增加"我在开发游戏"的沉浸感
- 给予 stability 数值变化的表象

#### 乐趣来源

- **看场景本身就是内容消费**（玩家看到正在做的 AVG 的片段）
- **找茬的轻松乐趣**（不需要动脑，纯观察）
- **"我发现 bug 了"的成就感**

#### 触发时机

- DevWork 中的"测试/Debug"任务

## 4. 林夏 Code Review 机制

### 4.1 概述

对话补全是唯一需要审查的小游戏。玩家提交的台词会通过 LinkChat 发送给林夏进行"Code Review"。

### 4.2 审查流程

```
玩家在小游戏中补全台词
	↓
提交 → 系统弹出 "正在提交PR..."
	↓
林夏在 LinkChat 中回复（LLM 审查）
	↓
┌────────────────────────────────────────┐
│ ✅ 通过 (APPROVE)                      │
│   林夏: "这句好诶！跟前面的氛围很搭"   │
│   → 台词 merge 到 AVG 项目             │
│   → 林夏短暂好感                       │
├────────────────────────────────────────┤
│ ⚠️ 建议修改 (REQUEST_CHANGES)          │
│   林夏: "嗯... 意思我懂但有点突兀？     │
│         要不改成'我其实早就察觉了'?"     │
│   → 玩家选择:                          │
│     - 接受建议 → 用林夏的版本          │
│     - 坚持原文 → 二次提交              │
│     - 重写 → 回到小游戏界面            │
├────────────────────────────────────────┤
│ ❌ 拒绝 (REJECT)                       │
│   林夏: "......你认真的吗 😑"           │
│   → reject_count +1                   │
│   → 玩家可以重写重新提交               │
└────────────────────────────────────────┘
```

### 4.3 多次拒绝机制

```
reject_count 达到阈值 (默认 3 次):
	林夏: "算了，这段我自己来写吧 😤"
	→ 当前任务结束
	→ 保留原有 AI 默认台词
	→ affection 可能微降（视关系状态而定）
```

### 4.4 LLM 审查 Prompt 要点

```
审查依据:
  - 当前场景的情绪基调 (如: 忧伤告别 / 轻松日常)
  - 前后文对话 (上下文连贯性)
  - 角色人设 (这个角色会说这种话吗)

判断标准:
  - 完全无关 / 乱写 / 恶搞 → REJECT
  - 风格稍有偏差但有诚意 → REQUEST_CHANGES + 给出修改建议
  - 合理且有个人特色 → APPROVE
  - 玩家选择选项（非自由输入）→ 默认 APPROVE（选项由系统保证质量）
```

## 5. 氛围型伪开发小游戏

这些小游戏**对 AVG 项目无实际影响**，纯粹用来增加 completion 数值和"我在开发游戏"的沉浸感。

### 5.1 代码打字（Typing Game）

**体验定位**：看上去在写很厉害的代码

**玩法**：
- LLM 生成一段看起来很专业但实际上无意义的伪代码（如 Java/GDScript 风格）
- 代码在屏幕上逐行显示，玩家像打字游戏一样逐字敲出
- 准确度和速度影响"效率评分"
- 完成后 completion +少量

```
┌─ 代码编辑器界面 ─────────────────────────────┐
│  1 │ public class SceneRenderer {            │
│  2 │   private void initializeContext() {    │  ← 灰色提示
│  2 │   private void initializeC█             │  ← 玩家正在打
│  3 │     var viewport = getViewport();       │
│    │                                         │
│    │  效率: ████████░░ 82%   连击: 12        │
└──────────────────────────────────────────────┘
```

**代码类型示例**：
- AVG 引擎渲染逻辑（伪）
- 对话系统解析器（伪）
- 场景转场效果计算（伪）
- 粒子系统参数调优（伪）

**乐趣来源**：打字爽感 + "我在写真正的代码" 的错觉

### 5.2 回复关注者留言

**体验定位**：社交媒体运营 — 和粉丝互动

**玩法**：
- Sbeam 或社交平台上出现关注者对游戏开发进度的留言/提问
- 玩家从 2-3 个回复选项中选择一个
- 不同回复影响 hype（热度）数值
- 偶尔出现恶意评论，选择是否回应

```
┌─ Sbeam 社区页面 ─────────────────────────────┐
│  🎮 [游戏名] 开发日志 #3                      │
│                                              │
│  💬 小明同学: "这个游戏什么时候出？好期待！"   │
│                                              │
│  回复选项:                                    │
│  A. "正在加紧开发中！敬请期待 😊"   → hype +2 │
│  B. "快了快了，不要催！"           → hype +0 │
│  C. [不回复]                       → hype -1 │
│                                              │
│  💬 杠精: "又一个跳票的独立游戏"              │
│  A. "我们会用作品说话"             → hype +1 │
│  B. "你行你上"                     → hype -2 │
│  C. [不回复]                       → hype +0 │
└──────────────────────────────────────────────┘
```

**乐趣来源**：社交互动感 + 粉丝经营 + 偶尔的搞笑评论

### 5.3 其他可选氛围小游戏（待设计）

以下为候选，后续可按优先级逐个细化：

| 小游戏 | 形式 | 体验 |
|--------|------|------|
| 写 Git commit message | 从 3 个选项中选提交信息 | "我在管版本" |
| 搜 Stack Overflow | 浏览伪搜索结果，选一个"解决方案" | "查 bug 的日常" |
| Build 等待 | 进度条 + 随机有趣的编译信息 | "等编译的焦虑感" |
| 选变量名 | 给一个函数/变量从 3 个名字里选一个 | "命名是最难的事" |

### 5.4 氛围小游戏设计原则

1. **对项目无实际影响** — 纯 completion 数值变化
2. **单次时长 ≤ 2 分钟** — 不能拖沓
3. **不需要真实技能** — 非程序员也能玩
4. **有"开发感"** — 界面模拟代码编辑器/终端/论坛
5. **可复玩** — LLM 每次生成不同的代码/留言内容

## 6. 玩家产出注入管线

### 6.1 两种注入机制

#### 机制 A：槽位替换（精确嵌入）

**适用于**：对话补全

Worker LLM 生成 AVG DSL 时预留标记槽位：

```dsl
# LLM 生成的 DSL（带槽位）
bg.show("bg_rain_station", fade_duration=0.5)
char_001.show(position="center", emotion="sad")

> 你真的要走吗？

# => PLAYER_SLOT: dialogue_03_line2
> {{PLAYER_DIALOGUE_03}}

> ...我知道了。
```

玩家小游戏通过审查后，精确替换：

```dsl
# 最终 DSL
bg.show("bg_rain_station", fade_duration=0.5)
char_001.show(position="center", emotion="sad")

> 你真的要走吗？
> 不是想走，是不得不走
> ...我知道了。
```

#### 机制 B：上下文注入（影响后续生成）

**适用于**：玩家风格偏好积累

玩家的累计选择（选了哪些词磁铁、写了什么风格的台词）统计为风格偏好，注入 LLM 的 prompt context：

```
# 注入到 PromptPipeline 的 vars 中
player_style_context:
  玩家的创作偏好（从历史操作统计）:
  - 对话风格: 简洁含蓄 > 长篇抒情 (6:2)
  - 情感倾向: 克制 > 外放 (5:3)
  - 节奏偏好: 先铺垫后爆发

  请在生成后续场景时参考以上偏好。
```

### 6.2 存储结构

```json
{
  "player_contributions": {
	"dialogue_fills": [
	  {
		"scene_id": "scene_03",
		"slot_id": "dialogue_03_line2",
		"text": "不是想走，是不得不走",
		"status": "approved",

	  {
		"scene_id": "scene_08",

		  "condition": "choice == '离开'",
		  "true_branch": {"bg": "sunset", "bgm": "melancholy"},

	  }
```

### 6.3 管线集成架构

```
					┌─────────────────────┐
					│   Story Director    │
					│ (completion 阈值触发) │
					└─────────┬───────────┘
							  │ 决定生成哪个场景
							  ▼
┌──────────────┐    ┌─────────────────────┐
│ 玩家小游戏    │    │  AVGSceneGenerator  │
│ 对话补全 ────┤    │                     │
│ 伪代码拼图 ──┤    │  1. 查询玩家贡献     │
│ Bug修复 ─────┤    │  2. 注入 style_stats │
│              │    │     到 prompt vars    │
└──────┬───────┘    │  3. 调用 LLM 生成    │
	   │            │     AVG DSL（含槽位） │
	   │            └─────────┬───────────┘
	   │                      │
	   ▼                      ▼
┌──────────────┐    ┌─────────────────────┐
│ PlayerContri-│    │  SlotReplacer       │
│ butionStore  │───▶│  (后处理)            │
│ (autoload)   │    │  替换 {{PLAYER_XX}}  │
└──────────────┘    │  为玩家的实际产出     │
					└─────────┬───────────┘
							  │
							  ▼
					┌─────────────────────┐
					│   AVG Runtime       │
					│   播放最终内容       │
					└─────────────────────┘
```

### 6.4 集成到现有系统的关键改动

1. **新增 `PlayerContributionStore` (autoload)**
   - 管理所有玩家产出的存储与查询
   - 提供 `get_fills_for_scene(scene_id)` 查询接口
   - 提供 `get_style_stats()` 获取累计风格统计

2. **修改 `PromptPipeline.build_prompt()`**
   - 在 vars 中新增 `player_style_context` 变量
   - 从 `PlayerContributionStore.get_style_stats()` 动态构建

3. **新增 `SlotReplacer` 后处理模块**
   - 在 DSL 解析后、Runtime 播放前执行
   - 扫描 `{{PLAYER_XXX}}` 标记并替换为实际产出
   - 未被替换的槽位保留 LLM 的默认文本

4. **新增 `CodeReviewTopic` 话题类型**
   - 玩家提交台词后通过 LinkChat 触发
   - 使用专门的审查 prompt 让 LLM 判断
   - 返回 APPROVE / REQUEST_CHANGES / REJECT

## 7. 小游戏与项目进度的关系

| 小游戏 | 对项目数值的影响 | 对 AVG 内容的影响 |
|--------|----------------|-----------------|
| 对话补全（三选项+自由输入） | completion +少量 | ⭐ 真实嵌入台词 |
| 伪代码拼图 | completion +少量 | 分支结构 |
| Bug 修复（找茬） | stability +少量（伪数值） | 无 |
| 代码打字 | completion +少量 | 无（纯氛围） |
| 回复关注者留言 | hype +少量 | 无（纯氛围） |

**项目的主要进度推进**来自 Worker LLM 的自动生成，不依赖小游戏的产出量。小游戏是"锦上添花"而非"必要条件"。

## 8. 设计总结

### 玩家体验

> "我和搭档一起做了一款 Gal Game。
> 主角是我设计的——一个从边境村庄来的元气少女，名字是我取的。
> 那个腹黑王子的性格也是我选的。
> 第三章有一句告白台词是我写的，林夏 review 的时候说这句她最喜欢。
> Demo 出来的时候，所有角色都在用我定义的方式说话——这是我的作品。"

### 系统真相

> 故事骨架由开发者预制，固定不变。
> 玩家的创意填充（人设、性格、台词）注入 LLM 的生成 context。
> LLM 在约束框架内实时生成完整 AVG 内容。
> 每个玩家的产出因创意填充不同而独一无二。
> 林夏的 Code Review 既是质量控制，也是关系互动。
