# 表层想法与底层 Worker 传话方案整理

## 文档目的

这份文档是给后续开发前做 review 用的。

重点回答两个问题：

1. 玩家在表层系统里说出的想法，应该怎样稳定地送到底层 worker LLM。
2. 底层 worker LLM 在执行过程中产生的新需求、疑问、阶段结果，应该怎样再传回表层，让玩家感受到“搭档真的在和我一起做东西”。

---

## 本次整理的范围

这次整理只看**还要继续保留的系统**。

明确排除：

- `DeepCode`（旧的开发聊天 App）已经废弃，后续会删除。

所以，后面的方案不再把 `DeepCode` 当成正式入口，只把它当成一段旧实现参考。

## 当前项目里，真正还有效的上下层链路

### 一、底层执行中心，其实已经比较统一

你现在真正负责“后台干活”的中心，已经基本统一到这条链上：

`WorkOrderManager`（工单总管，负责派发任务）  
→ `WorkOrderControllerAgent`（工单控制代理，负责判断怎么做）  
→ `Planner / Writer / Executor`（三个子代理，分别负责策划文案、脚本实现、机械修改）

并且你已经做了 `trunk`（临时工作副本）机制：

- 底层先在临时副本里修改。
- 完成后再合并回主工程。
- 这样不会把半成品直接写到玩家看到的主工程里。

这部分方向是对的，不建议推翻。

### 二、表层目前有 4 个仍然有效的想法入口

#### 1. `DevWorkApp`（开发任务列表）

这是最像“养成游戏表层操作”的入口。

玩家看到的是“做任务”。

系统内部实际有两种流向：

- 如果任务是 `chat_topic`（聊天讨论型任务），就先进入 `LinkChat`（聊天系统），和林夏讨论。
- 如果任务带 `work_order_template`（预设工单模板），就直接变成后台工单，静默执行。

也就是说，它已经有“表层任务”和“底层开发”之间的翻译层。

#### 2. `LinkChat`（聊天系统）

这是最像“玩家直接说想法”的入口。

玩家在聊天里说的话，会进入：

`LinkChatApp`（聊天界面）  
→ `ChatManager`（聊天总管）  
→ `ChatPromptBuilder`（提示词拼装器）  
→ LLM

更重要的是，聊天系统已经支持**协议动作**。

也就是 NPC 不只是回文字，还可以在回复里夹带类似：

- `[generate_work_order ...]`
- `[open_browser ...]`
- `[post_moment ...]`

这样的动作请求。

这意味着：

- 聊天已经不只是“演出”。
- 聊天已经可以开始驱动真正的游戏系统。

#### 3. `StoryDirector`（剧情导演）

剧情步骤本身也可以直接触发：

- `dispatch_work_order`（直接创建并派发工单）
- `generate_work_order`（先用 LLM 生成工单，再派发）

这条链更像“剧情脚本替玩家安排任务”。

它适合做强编排内容，比如：

- 第一天必须先讨论主题
- 某个剧情点触发新的制作任务
- 某个事件后自动把讨论内容整理成任务

#### 4. `WorkOrderApp`（工单面板）

这个入口最直接，也最像调试台。

玩家可以手动创建工单并派发。

它当然能继续保留，但更适合作为：

- 调试入口
- 少量高自由度玩法入口

它不太像“主体验入口”。

## 当前项目里，底层回传给上层的能力，已经预留了什么

### 一、已经预留但还没有真正接通的两个回传口

`WorkOrderManager` 里已经有两个很关键的函数：

- `request_clarification`（请求玩家补充说明）
- `request_creative_task`（请求玩家参与创意讨论）

它们的方向是对的：

- `request_clarification` 会把底层疑问抬到 `LinkChat`，让 NPC 用自然聊天的方式追问玩家。
- `request_creative_task` 会通知 `DevCycleManager`（开发循环总管）创建新的讨论任务，让玩家亲自参与创意决策。

这说明你的设计直觉已经非常接近目标了：

- 底层不是只能闷头干活。
- 底层是可以“抬头找玩家商量”的。

### 二、但这两个回传口现在还没有真正变成 worker 可用工具

目前的问题不是“没有方向”，而是“最后一段线没有插上”。

我检查下来，现状是：

- 管理函数已经有了。
- 但是它们还没有正式注册成 Controller 或子代理能调用的工具。
- 相关 prompt 里也没有系统地教 worker：什么时候该追问，什么时候该拉玩家讨论。

结果就是：

- 代码层面允许“上浮”。
- 但实际运行时，底层 agent 还不能稳定地主动这样做。

这正是你当前最关键的缺口。

## 当前结构的主要问题

### 1. 入口很多，但没有统一的“玩家想法包”

现在玩家的想法可能来自：

- 开发任务按钮
- 聊天讨论
- 剧情强制触发
- 手动工单

但这些输入进到底层之前，没有被统一整理成同一种结构。

于是底层看到的东西有时是：

- 一段自然语言
- 一段聊天记录
- 一个任务模板
- 一个剧情 action

这会让后面的判断逻辑越来越散。

### 2. 回传很多种，但没有统一的“底层回执包”

底层向上层表达的内容，其实大致只有几类：

- 我缺信息，请补充
- 我需要和玩家讨论一个创意分叉
- 我完成了一个阶段，请告诉玩家
- 我已经做完了，请安排展示
- 我卡住了，请换路或回退

但现在这些类型没有统一的字段结构。

于是：

- 有的走聊天
- 有的走日志
- 有的走状态
- 有的还没有真正接通

### 3. `WorkOrder`（工单）状态还不够表达“来回沟通”

现在工单的表层状态主要是：

- `pending`
- `in_progress`
- `completed`
- `needs_input`

这已经比单一状态好很多了，但如果要真正做“玩家和底层来回协作”，还不够细。

至少还会需要表达：

- 等玩家确认
- 正在讨论创意
- 已生成阶段成果，等待展示
- 已完成，但还没让玩家看到
- 因条件不足而阻塞

### 4. 讨论结果到工单，已经有；工单执行中再回找玩家，还没有闭环

你已经实现了：

- 玩家和林夏讨论
- 系统从讨论里生成工单
- 工单进后台执行

但还没有真正实现：

- 工单做到一半发现缺东西
- 底层主动发起澄清
- 玩家补充后继续执行

也就是说，现在是“能下去”，但“还不能自然地再回来”。

### 5. `DeepCode` 这条旧线会干扰判断

因为 `DeepCode` 是一个“玩家直接对 AI 说话、马上改工程”的旧入口，
它会天然把人带回“工具型开发助手”的思路。

但你这个项目更想做的是：

- 搭档共创
- 讨论与取舍
- 表层体验和底层制作错位
- 黑箱开发 + 阶段性揭晓

所以它删掉是对的。

删掉之后，设计就会更聚焦：

- 玩家不是在“用 AI 工具”。
- 玩家是在“和搭档一起推进一个会自己运转的创作过程”。

## 方案一：纯工单中心方案

### 核心想法

无论玩家从哪里表达想法，最后都先整理成一张工单，再交给底层。

也就是说：

- 聊天输入也变工单
- 任务点击也变工单
- 剧情触发也变工单
- 所有底层执行都只认工单

### 表层怎么往下传

先定义一个统一的“玩家想法记录”。

可以叫：

`surface_intent`

它不是给玩家看的，而是给系统内部用的。

建议至少有这些字段：

- `source_type`：想法来自哪里，比如 `linkchat`、`dev_task`、`story_event`
- `source_id`：来源对象的编号
- `player_text`：玩家原话
- `npc_id`：当前是和谁一起讨论
- `goal_type`：玩家想做的是“确认方向”“补充细节”“正式派工”“只是随口聊聊”
- `confidence`：系统对这次理解有多确定
- `constraints`：当前已知限制，比如世界观限制、阶段限制、资源限制
- `suggested_route`：建议走“先讨论”还是“直接派工”

然后系统统一做一步判断：

- 如果信息很完整，直接转工单。
- 如果信息不完整，先转成澄清话题。
- 如果它本质是创意分叉，先转成讨论任务。

### 底层怎么往上回

统一定义一个“底层回执”。

可以叫：

`worker_feedback`

建议至少有这些类型：

- `need_clarification`：缺少具体信息
- `need_creative_discussion`：需要玩家参与创意选择
- `status_update`：阶段进度更新
- `milestone_ready`：阶段成果已经能展示
- `delivery_ready`：最终结果已完成
- `blocked`：遇到阻塞

然后上层根据类型决定怎么呈现：

- `need_clarification` → 开一个 LinkChat 澄清话题
- `need_creative_discussion` → 在 `DevWorkApp` 里生成讨论任务，或者直接开聊天
- `status_update` → 放进工单面板或系统通知
- `milestone_ready` → 触发预览、Demo、文件预览、消息提醒
- `delivery_ready` → 标记完成，等待合适时机展示

### 优点

- 底层逻辑最统一。
- 所有开发行为都能追踪。
- 后面做存档、回放、统计会很顺。
- 对多入口输入最友好。

### 缺点

- 玩家会更少直接感受到“聊天本身正在推动创作”。
- 如果什么都变工单，体验上可能显得太像管理系统。
- 需要额外做一层“自然化包装”，不然会显得生硬。

### 适合你吗

适合作为**技术底座**，但不建议直接拿它当最终的玩家体验外壳。

## 方案二：纯聊天主导方案

### 核心想法

玩家所有重要想法，都先通过 `LinkChat` 和林夏讨论。

只有当聊天里形成共识后，系统才自动生成工单并进入后台。

也就是说：

- 聊天是主入口
- 工单是聊天之后的后台产物

### 表层怎么往下传

流程会变成：

玩家想法  
→ `LinkChat` 聊天  
→ NPC 追问 / 整理  
→ 聊天协议动作 `[generate_work_order ...]`  
→ 自动生成工单  
→ 后台执行

### 底层怎么往上回

底层如果需要更多信息，也统一回到聊天：

- 要补充信息，就发起澄清聊天
- 要讨论创意，就发起新话题
- 要汇报结果，就让林夏主动来找玩家发消息

### 优点

- 最像“恋爱共创游戏”。
- 玩家会很自然地感受到“我是在和搭档聊出来一个作品”。
- 人物关系、创作关系、任务推进会合得很紧。

### 缺点

- 对明确任务的处理效率会下降。
- 很多重复性开发内容，如果也强行走聊天，会显得拖。
- 聊天需要写得非常好，否则很容易变成低信息量寒暄。

### 适合你吗

适合作为**概念期、创意期、关系推进期**的主方案。  
不太适合作为整个开发周期的唯一方案。

## 方案三：双轨方案

### 核心想法

玩家的输入先按性质分流：

- **模糊的、创意型的、需要共识的** → 先聊天讨论
- **明确的、执行型的、已经定好的** → 直接变工单

底层执行仍然统一走工单系统。

也就是说：

- 表层是双轨
- 底层是单轨

### 这是最接近你当前项目气质的方案

它既保住了：

- 聊天恋爱感
- 共创感
- 讨论和取舍

又保住了：

- 后台开发黑箱
- 统一执行中心
- 阶段性揭晓

### 玩家想法如何分流

建议做一个很简单的判断层。

不用追求“特别聪明”，只要足够稳就行。

可以按下面规则判断：

#### 直接进聊天讨论

当玩家说的是：

- “我觉得这段应该更虐一点”
- “女主是不是别太主动”
- “世界观要不要换成近未来”
- “这里到底做乙女还是普通向”

这种话，本质上不是命令，而是在表达方向、口味、偏好、犹豫。

这类应该先进 `LinkChat` 讨论。

#### 直接进工单

当玩家说的是：

- “把讨论结果整理成角色设定”
- “根据现在的大纲写第一章”
- “把这个场景改成雨夜版本”
- “把女主名字统一成林夏”

这类已经非常明确，适合直接进入工单。

#### 先澄清再决定

当玩家说的是：

- “这个地方不太对”
- “我想改一下”
- “总觉得差点意思”

这种信息明显不够，应该先由系统判断为：

- 不是直接派工
- 先开一个澄清话题

### 底层怎么回到上层

双轨方案下，底层回传也按两类分流：

#### 回聊天

用于：

- 缺少口味判断
- 需要玩家拍板
- 需要林夏和玩家一起争论一个创意分叉

#### 回系统

用于：

- 进度提示
- 工单完成
- 阶段成果可展示
- 预览入口可解锁

### 优点

- 最符合你的游戏目标。
- 不会让所有内容都变成聊天，也不会让所有内容都变成冷冰冰的工单。
- 技术上可以继续复用你现在已有的大部分代码。

### 缺点

- 需要补一个稳定的分流层。
- 需要统一“聊天结束后怎么落到底层”的规则。
- 需要补“底层上浮工具”的最后一段接线。

### 适合你吗

**最适合。**

如果只选一个产品方案，我建议选这个。

---

## 三种方案对比

| 方案 | 玩家感受 | 系统稳定性 | 恋爱共创感 | 开发成本 | 是否推荐 |
|---|---|---:|---:|---:|---|
| 纯工单中心 | 更像任务管理 | 高 | 中 | 中 | 可做技术底座 |
| 纯聊天主导 | 更像搭档共创 | 中 | 高 | 高 | 适合局部，不适合全程 |
| 双轨方案 | 兼顾任务与关系 | 高 | 高 | 中高 | 最推荐 |

---

## 我推荐的最终路线

不是“只选一种”，而是分成两层来看。

### 产品层

用**双轨方案**。

也就是：

- 创意问题先聊天
- 明确任务直接派工

### 技术层

用**工单中心方案**做底座。

也就是：

- 所有真正进入后台执行的事情，最后都统一变成工单
- 所有底层回传，也都统一变成标准回执

这样组合起来以后，会是：

玩家体验上像“双轨共创”  
系统实现上像“单中心执行”

这是最稳的。

## 建议的统一数据结构

下面这部分不是要你现在立刻全做完，而是为了后面开发时不再反复改方向。

### 一、表层输入统一成 `surface_intent`

建议字段：

```json
{
  "intent_id": "intent_xxx",
  "source_type": "linkchat",
  "source_id": "dm_lin_xia",
  "player_text": "我觉得这里不要太甜",
  "npc_id": "npc_lin_xia",
  "intent_kind": "creative_preference",
  "confidence": 0.62,
  "constraints": {
	"phase": "concept",
	"story_topic": "heroine_design"
  },
  "suggested_route": "discussion_first"
}
```

### 二、底层上浮统一成 `worker_feedback`

建议字段：

```json
{
  "feedback_id": "wf_xxx",
  "order_id": "wo_12",
  "type": "need_clarification",
  "title": "还缺一个关键信息",
  "message": "女主更偏温柔还是更偏嘴硬？",
  "questions": [
    "更偏温柔，还是更偏嘴硬？"
  ],
  "preferred_surface": "linkchat",
  "npc_id": "npc_lin_xia"
}
```

### 三、阶段成果统一成 `delivery_ticket`

建议字段：

```json
{
  "ticket_id": "delivery_xxx",
  "order_id": "wo_12",
  "delivery_type": "scene_preview",
  "title": "第一章初稿可以看了",
  "summary": "已经完成第一章的剧情草稿和基础场景切换。",
  "open_app": "game_previewer",
  "target_id": "scene_001"
}
```

## 最值得先做的 5 件事

### 1. 正式把底层上浮工具接通

也就是把下面两个函数，真正注册成 worker 可调用工具：

- `request_clarification`
- `request_creative_task`

这是当前最核心的一步。

不做这一步，底层就始终只能“往下执行”，不能自然地“回头找玩家”。

### 2. 增加一个输入分流层

让系统先判断：

- 这是直接派工
- 这是先讨论
- 这是先澄清

这层可以很简单，不一定一开始就要用复杂模型。

### 3. 扩展工单状态

建议至少加上：

- `awaiting_player`
- `discussion_required`
- `milestone_ready`
- `blocked`
- `delivered`

这样表层就能更自然地表现“搭档正在等你”“这里卡住了”“新内容能看了”。

### 4. 给工单补“来源信息”

每张工单最好能知道自己来自哪里。

比如：

- 来自哪次聊天
- 来自哪个表层任务
- 来自哪个剧情步骤

这样后面做：

- 回放
- 归因
- 阶段汇报
- 存档恢复

都会顺很多。

### 5. 把“完成”拆成“做完”和“展示给玩家”

这件事很重要。

你这个游戏不应该让“后台写完了”立刻等于“玩家已经看到了”。

建议分成两层：

- 底层完成了开发
- 上层安排一个合适时机展示成果

这样才能保住“阶段 Demo / Build 才看到惊喜”的感觉。

## 一个适合你项目气质的完整流程示例

下面这个例子，最能说明我为什么推荐“双轨表层 + 工单底座”。

### 例子：玩家说“我觉得女主别太主动，稍微拧巴一点更有意思”

#### 第一步：系统判断输入性质

这不是明确命令。  
它更像创作偏好。

于是系统不直接派工，而是生成一个 `surface_intent`，并判断为：

- `intent_kind = creative_preference`
- `suggested_route = discussion_first`

#### 第二步：进入聊天讨论

林夏在 `LinkChat` 里接这个球，和玩家聊两三轮。

目标不是马上写文档，而是确认：

- 你说的“别太主动”具体指什么
- 是嘴硬、别扭、慢热，还是别的

#### 第三步：讨论达成共识

讨论结束时，NPC 通过协议动作或系统逻辑，生成一张工单。

这张工单写的不是“玩家说想改一下”，而是更明确的执行要求，比如：

- 更新女主角设定文档
- 补充她的情感推进方式
- 保持前期慢热，不要直接进入强烈表白模式

#### 第四步：底层开始执行

Controller 读取工单后，判断这是策划文案类任务，于是交给 `Planner`（策划文案子代理）去写 KB。

#### 第五步：底层发现信息还差一点

如果它在写的过程中发现：

- “慢热”可以有两种完全不同的写法

它就不应该硬写。

这时它应该上浮一个：

- `need_clarification`

然后系统再让林夏回到聊天里，补一句：

- “你说的拧巴，是偏嘴硬那种，还是偏压着不说那种？”

#### 第六步：玩家补充后继续执行

玩家回答后，底层恢复执行。

#### 第七步：底层完成，但不一定立刻曝光全部结果

底层完成以后，可以只回一个：

- `milestone_ready`

比如：

- “女主设定已经整理好了”
- “这次修改会影响后面几段剧情表现”

但真正看到完整效果，可能要等下一次 Demo 或剧情播放。

这就很符合你想做的“黑箱共创”感觉。

---

## 我对当前路线的最终建议

一句话总结：

**不要再把“玩家想法传给底层”理解成单一输入框问题，而要把它做成一套完整的来回协作协议。**

更具体一点说：

1. 删掉 `DeepCode` 后，正式把主入口收敛到 `DevWork + LinkChat + StoryDirector + WorkOrder` 这几条线上。
2. 表层采用双轨：模糊创意先聊，明确任务直派。
3. 底层继续统一走 `WorkOrderControllerAgent` 这条执行链。
4. 尽快把 `request_clarification` 和 `request_creative_task` 接成正式工具。
5. 把“完成开发”和“把成果展示给玩家”拆开。

如果照这个方向走，你后面做出来的感觉会更像：

- 玩家和搭档一起做游戏

而不是：

- 玩家在虚拟 OS 里调用一个 LLM 工具。
