各位评委老师好，我是《游戏女孩轻度依赖》的开发者

在正式介绍之前，请大家先看一段实机演示。

大家刚才看到的，我们的游戏只是一款实验性很强的 Demo。它无法与完整作品比较，所以今天我主要讲两个问题：为什么做，以及我怎样把这个想法真正做出来。

为什么我想做一款关于“做游戏”的游戏。这两年，“一句话生成游戏”正在从概念变成产品。TapTap 制造尝试通过对话完成程序、美术和音乐，光子的造化工坊则可以从故事设定生成互动影游。它们描绘的未来很诱人：人负责创意，AI 负责实现。

但是，游戏开发者社区里一直流传着一句很残酷的话：“你的前十款游戏都会很糟。”只有经历完成、测试、失败和迭代，才可能逐渐理解什么是好玩的游戏。

AI 可以降低代码和美术的门槛，却不能替创作者跳过这些失败。2025 年以来 Steam 约有五分之一的新游披露使用了生成式AI，但绝大部分作品甚至赚不回上架费。AI 可以帮助更多人做出第一款游戏，却不一定能让他们做到第十一款。

于是，AI 游戏生成软件似乎陷入了一个尴尬的位置：

对于真正的开发者，它的控制力和上限可能还不够；对于没有开发经验的普通用户，它又很容易变成一个体验几次就放下的玩具。

难道 AI 生成游戏最终只会是一块鸡肋吗？

这让我想起了自己的第一款游戏。它同样是彻头彻尾的垃圾，但高中时，我和一个好朋友会在晚自习偷偷讨论，午休再挤出半小时敲代码。直到今天，我怀念的不是那款游戏做得有多好，而是当时和我一起做游戏的人。

因为人的参与，那款垃圾游戏对我有了意义。

所以我开始想：既然 AI 暂时不能保证普通人做出精品，能不能先让一款并不完美的游戏对作者产生意义？何不把“做游戏”本身做成游戏，让玩家与一个有性格、有情绪的角色共同创作，最后得到一款记录他们选择与经历的作品？

如果是一个头脑正常的程序员，大概不会开发这种吃力不讨好的东西。但可惜，我的程序员是 AI，它压根没有脑子；而我只是一个疯狂的策划。

不过，一旦决定让玩家在游戏里做游戏，第一个现实问题就出现了：他们究竟要做什么类型的游戏？

我本人是历史学院的学生，不可能在个人项目里重新发明一套什么都能做的全能引擎。如果我真能设计出来，在座的程序员老师们可能就要考虑失业问题了。

更重要的是，“什么都能生成”未必适合现阶段的 AI。我参加过一场只能使用 TapTap 制造开发的 48 小时 GameJam。在极限创作环境里，它非常好玩；但回到AI生成游戏本身，不同创意又很容易长成相似的 UI 和原型。一旦追求完整内容和独特体验，游戏开发的复杂度就会重新出现。

那么，什么类型既不需要维护一个无限膨胀的工程，又能够保留作者的独特表达？

造化工坊给了我一个启发。它把创作集中在故事树、分镜、台词上。程序框架保持稳定，真正变化的是作者的故事与选择。这既降低了 AI 的理解难度，也保证了作品的基本下限。

因此，我把玩家最终制作的作品限定为视觉小说。视觉小说的框架可以保持不变，变化集中在故事本身上。

限定类型只解决了“做什么”，还没有解决“AI 怎样把它真正做出来”。如果我仍然让 AI 根据玩家的每次选择，直接修改一个不断变化的代码工程，那么游戏开发的复杂度，很快又会回来。

所以，我需要先给 AI 准备一种结构稳定的工程形式。

我没有从零发明 AVG 引擎，而是拆解融合了 RPG Maker 的数据化工程、橙光等成熟AVG编辑器的剧本指令和代码语言，以及 Godot 的节点系统。角色、场景、变量和伪代码保存在外部文件里，运行时，Godot 读取数据、创建节点树并执行演出。

这样一来，AI 不需要维护真正的代码工程，只需要修改一套规则明确的 AVG 数据。但框架只提供了一个可以修改的对象，AI 还缺少真正操作工程的手。

于是，我让 Codex 干了一件很符合它身份的事情：抄袭它自己的 harness。

我把 Codex 拆解任务、挂载 Skill 和调用 Tool 的方式移植进游戏。

例如，剧情可达性 Tool 会从初始场景开始做一次伪运行，追踪场景跳转和变量变化，找出没有入口的孤立场景，以及按照现有条件永远无法进入的“假分支”。Agent 因此能够形成“修改、检查、再修改”的循环，而不是一次性生成一段看起来正确的文字。

所有 AI 提示词的排序方式又由 PromptManager 统一管理，通过固定稳定内容的排列，大部分请求都能获得 95% 以上的提示词缓存命中率。

到这里，我解决了AI开发底层问题：AI 已经能够读取工程、修改内容，并检查自己的结果。生成人类可以游玩的AVG。

但如果把这些内容直接摆在玩家面前，我做出来的仍然只是一个开发工具，而不是一款游戏。所以下一个问题是：玩家应该通过什么形式参与这场创作？

我最初给出的答案，是一套桌面 OS。玩家始终停留在同一个空间，功能可以收进不同 App；聊天窗口和输入框也天然适合一款需要玩家表达想法的 AI 原生游戏。

在这个桌面上，我照着游戏公司的实习经历，把玩家设计成策划实习生：填写工单、分配给程序和美术、通过聊天软件对齐需求，甚至直接打开引擎App 修改工程。

这套设计在逻辑上能够成立，但各位老师应该已经发现了：它拟真到了完全不好玩的地步。流程复杂、理解成本很高、即时反馈又很少。

为什么会走错？因为我最初只在思考“怎样模拟开发”，却忘记了自己为什么要做这款游戏。真正让第一款游戏产生意义的，而是和玩家一起做游戏的人。

因此，我舍去了多工种角色和游戏公司的背景。玩家变成一名即将毕业的大四学生；毕业前夕，他的女朋友希望两个人一起完成一款真正属于他们的作品。我要强调的不再是“游戏开发”本身，而是一个关于“共同开发游戏”的故事。

为此，我加入了故事线管理系统。随着日期推进，两个人会报名参赛、面对家人与同学不解，并在阶段节点一起试玩 Demo。主线、情绪目标和重要 CG 由我提前设计；AI 只根据当局经历调整对话、细节与局部分支。

这时，原本的桌面系统也变成了两个人共同生活的空间：玩家可以聊天、浏览网站、填写报名信息，也可以从桌面进入 AVG 剧情。

与此同时，我雪藏了工单 App 和引擎 App。工程对玩家变成黑箱，只有抵达里程碑时，女主才会邀请玩家试玩阶段版本。玩家等待的是一个阶段性的答案：我们共同做的东西，究竟变成了什么？

这既降低了理解成本，也拉开了玩家与工程的距离。长期测试很容易让开发者对项目麻木；我希望每次试玩都成为关系与项目共同前进的里程碑，保留第一次看到成果的惊喜。

不过，把工程藏起来之后，又产生了一个新的问题：如果玩家不能直接编辑文件，他怎样在最终作品中留下自己的创作？

我曾经把答案寄托在自由输入上，但它会把玩家推向两个极端。有表达欲的玩家写得越多，就越期待 AI 完整理解和兑现；另一类玩家面对空白输入框，却根本不知道应该写什么。同一个输入框，一部分玩家期望太高，对另一部分玩家要求得太多。

所以，我把开发环节抽象成小游戏。内部策划 Agent 先写好隐藏工单，再把适合玩家参与的部分包装成桌面小游戏。玩家的小游戏结果随后被整理成结构化信息，注入工单，由底层 Agent 修改工程。

小游戏分为两类。氛围型只提供“我正在开发”的操作感，例如把写代码变成打字游戏；创作型则真正改变作品，例如剧本填空同时提供候选台词和局部补写，策划讨论只要求玩家表达大致方向，再由 AI 整理成可执行方案。

玩家的想法被整理成工单之后，最后一个问题也随之出现：这个 Agent 不是只回复一句话，它需要读取项目、调用工具、修改工程、验证和返工，因此不可能瞬间完成。

我们本质上是游戏，而不是让用户盯着进度条的工具。所以我借鉴《主播女孩重度依赖》的状态和行动设计，限制每个时段能够触发的开发行动，再加入约会、购物和一起打游戏等生活事件。

这些事件会根据当前状态和历史记录生成，再由轻量 Agent 临时制作成短篇 AVG。玩家只需在地图上选择地点，系统自动发出邀请；场景回应也以预生成选项为主。

说得直白一点，这是一个“拖”字诀：玩家正在和女主过剧情，开发 Agent 则在后台偷偷完成工单。我不需要让 Agent 在一瞬间完成真实工作，只需要保证在它工作的时候，游戏仍然能够继续。

至此，表层与底层才算是连在一起：玩家在表层经历关系、作出选择，并通过小游戏表达创意；Agent 在底层完成开发；最终成果再通过剧情变化和里程碑 Demo，重新回到两个人的故事里。

当然，《游戏女孩轻度依赖》仍然只是一款实验性质很强的 Demo。我没有解决 AI 创作中的所有问题，它也远远谈不上完整、成熟、好玩。

但我想借它探索一种可能：AI 创作除了成为提高效率的工具，能不能也成为一种游戏机制？

今天，我们尝试让玩家和一个 AI 角色共同制作游戏。未来，也许玩家可以和一个角色一起画完漫画，或者与一群不同性格的 AI 成员组建乐队。

AI 创作作为工具都仍在摸索，把它设计成有趣、有情感的游戏还要更远。但也许有一天，玩家打开一款游戏，最后带走的不只是一个故事，还有一件共同创作的作品。

谢谢各位老师。
